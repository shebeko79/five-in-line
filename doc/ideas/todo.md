# Убрать &k= &n= &w= &f= из вывода solver
Логичнее было бы, чтобы solver выводил их в том виде, чтобы скормить db.

Исторически была странная ситуация, когда solver формировал параметры сразу для отправки HTTP запросом.
Потому что распаралеливание было реализовано через .bat файлы.
Сейчас оно управляется питоном, правильнее было бы, чтобы питон формировал нужный HTTP запрос

# Пакетный get_job, save_job
При большом к-ве процессов сам HTTP запрос становится узким местом и не позволяет полностью загрузить процессы.
Необходимо получение сразу нескольких заданий одним HTTP запросом.
И сохранение сразу нескольких решенных состояний одним HTTP запросом.


# Итеративное увеличение бюджета и глубины поиска
Поменять solver, чтобы он последовательно запускал решения с разным бюджетом и с разной глубиной
Идея в том, что если какие-то ветки можно отсечь с меньшим бюджетом, то надо этим пользоваться.
Разная глубина возможно позволит отказаться от squeeze.

# Proof-Number Search (PNS)
Можно попробовать реализовать PNS в db. 
Proof Number и Disproof Number можно хранить в состоянии и relax() для их подсчёта хорошо ложится.

# Zobrist hashing
Стоит попробовать zobrist hashing в solver.
Не должно быть слишком тяжело, зато позволит отсеять дубликаты.
